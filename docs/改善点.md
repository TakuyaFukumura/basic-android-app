# 改善点

この文書は、現在の実装（v0.10.1）を基準に、今後取り組む改善候補を記録する。仕様変更や優先度の見直しに使える粒度で管理する。

## 現在の構成

- **UI**: Jetpack Compose、Material 3、ライト／ダークテーマ、Android 12 以降の動的カラー
- **アーキテクチャ**: `MainActivity` / `MainScreen` → `MainViewModel` → `StringRepository` → `StringDao` → Room
- **状態管理**: `MainUiState` を `StateFlow` で公開し、読み込み・CRUD・エラー状態を管理
- **データ**: Room v1、`strings` テーブル、初回作成時にデータが空の場合のみ `world` を投入
- **入力仕様**: 前後空白を除去し、100文字を上限とする。空文字は登録・更新しない
- **テスト**: ViewModelのJVMテスト、DAOのインメモリDBテスト、Compose UIテスト、基本的なInstrumentationテスト
- **CI**: Java 17、Android API 36、Lint・JVM単体テスト・Debug APKビルド。Instrumentationテストは手動実行時にエミュレーターで実施

## 改善方法の詳細

### CI: Pull RequestでInstrumentationテストを実行する

1. `ci.yml` の `pull_request` で実行するジョブと、手動・定期実行で実行するジョブを分ける。
2. Pull Request向けジョブでは、変更頻度の高いAPIレベルを1つに絞り、`reactivecircus/android-emulator-runner` で `connectedAndroidTest` を実行する。
3. テスト結果、スクリーンショット、Logcatを `if: always()` の成果物として保存する。エミュレーター起動時間が長いため、通常のLint・単体テストとは別ジョブにして並列化する。
4. まずPull Requestで安定して完走することを確認し、APIレベルの追加や定期実行はその後に検討する。

### リリース: 署名付きAPK/AABをWorkflowで生成する

1. `assembleRelease` の前に、GitHub Actions SecretsからBase64化したキーストアを一時ファイルへ復元する。キーストア、パスワード、別名はログへ出力しない。
2. `app/build.gradle.kts` の `signingConfigs` は環境変数またはGradleプロパティから値を読み込み、値がない場合は署名付きReleaseを生成できないよう明示的に失敗させる。
3. `workflow_dispatch` を入口にし、Environmentの承認ルールを使って公開担当者の確認後に実行する。タグ作成時に自動公開する場合は、先に同じ成果物の検証を行う。
4. `apksigner verify` または同等の手段で署名を検証し、APK/AAB、mappingファイル、テスト結果、チェックサムをActionsの成果物として保存する。

### データ層: RoomのMigrationTestとバックアップ／復元を追加する

1. スキーマを変更するときは、`@Database` のバージョンを上げ、KSPが出力する `app/schemas/` のJSONを同じ変更に含める。
2. `MigrationTestHelper` で旧バージョンのDBを作成し、Migration実行後に既存の文字列、主キー、NULL制約などが保持されることを検証する。
3. `Room.inMemoryDatabaseBuilder` のDAOテストとは別に、ファイルDBを使った移行テストを用意する。現在はv1のため、最初のスキーマ変更時に `1-to-2` のテストを追加する。
4. `backup_rules.xml` と `data_extraction_rules.xml` の対象を確認し、バックアップから復元したDBを起動できることを実機またはエミュレーターで確認する。

### UIテスト: 主要なユーザーシナリオを画面単位で検証する

1. `MainActivityUiTest` で実際の画面を起動し、入力、追加、編集保存、編集キャンセル、個別削除、全削除確認、キャンセルを順番に検証する。
2. `testTag` はテスト専用の識別子として維持し、ユーザーが見る文言は `stringResource` の文字列を使って検索する。
3. 空入力、100文字境界、読み込み失敗、操作失敗、再試行の表示をテスト対象にする。ViewModelはFake Repositoryを注入できる構成を利用する。
4. ダイアログの確認・キャンセル後に一覧と挨拶が期待どおり変わることまで確認し、単一Composableの表示確認だけに留めない。

### 依存関係: 脆弱性検出と更新検証を追加する

1. DependabotのGradle／GitHub Actions更新は維持し、`.github/workflows/dependency-review.yml` でGitHub Dependency ReviewをPull Requestへ追加する。
2. Dependency Reviewは新規のHighまたはCritical脆弱性を失敗条件とする。ライセンスは一律拒否せず、変更レビューで採用可否を確認する。
3. 依存関係更新時は既存のCIで `lintDebug`、`testDebugUnitTest`、`assembleDebug` を実行し、Compose・Room・Hiltの組み合わせに互換性問題がないことを確認する。
4. Dependency ReviewはGitHubの依存関係メタデータだけを検査し、ソースコードやSecretsを外部スキャンサービスへ送信しない。Actionsログにもトークンや環境変数を出力しない。

### 開発体験: フォーマットと静的解析を標準化する

1. Ktlint（Gradleプラグイン `12.2.0`、フォーマッター `1.7.1`）とDetekt（`1.23.8`）をVersion Catalogで固定する。
2. ローカルでは `.\gradlew.bat format` でKotlinを整形し、`.\gradlew.bat check` でKtlint検査とDetektを含む品質チェックを実行する。CIでは `ktlintCheck` と `detekt` を検査モードで実行し、自動修正を行わない。
3. 導入時の既存コードはKtlintで一度だけ整形し、以降は変更範囲を小さく保つ。CIでは既存のLint、単体テスト、Debugビルドと同じジョブで品質ゲートを適用する。

### 国際化: 多言語リソースとアクセシビリティ文言を整備する

1. `values/strings.xml` の表示文言とアクセシビリティ文言を翻訳対象として棚卸しし、言語ごとの `values-<言語>` リソースを追加する。
2. 文字列連結を避け、件数、入力値、削除対象などのプレースホルダーを使って翻訳順序を変更できるようにする。
3. RTL、長い翻訳、TalkBackでの読み上げを確認し、ボタンの説明とエラーの意味が視覚表示だけに依存しないことを確認する。
4. 対応言語をREADMEに明記し、端末の言語を切り替えたCompose UIテストまたは手動確認をリリース前チェックへ含める。

### 優先順位に関する補足

- Roomは現在v1でスキーマ変更がまだないため、MigrationTestは次のスキーマ変更と同時に追加する。
- CIにはDebugビルド、Lint、JVM単体テスト、Roomスキーマ出力が既に組み込まれている。Instrumentationテスト用のジョブは `workflow_dispatch` または `schedule` 条件で定義されているが、現行Workflowに定期実行トリガーはない。
- ReleaseビルドではR8とリソース縮小が有効だが、署名設定と公開用Workflowはまだない。
- `deleteAllStrings()` はViewModelから利用されているため、一覧が空になる操作自体は実装済みである。Undoやバックアップは未提供である。

## 推奨する実施順序

1. Release署名の運用要件を確定し、秘密情報をリポジトリへ保存しないWorkflowを追加する。
2. 主要な画面操作のCompose UIテストを追加し、Instrumentationテストの実行経路をCIで安定させる。
3. 次のRoomスキーマ変更時にMigrationTestとバックアップ／復元の検証を追加する。
4. 脆弱性スキャン、フォーマット・静的解析を段階的に導入する。
